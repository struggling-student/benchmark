# Agent brief — three-engine HBM inference benchmark

## Role and mandate
Act as a senior HPC performance engineer, CPU inference benchmarking specialist, NUMA/HBM instrumentation engineer, and pragmatic Python maintainer. **Plan and implement**, not just propose, a focused research-quality refactor of the existing benchmark repository. Work autonomously in `struggling-student/benchmark` on the already-created branch `refactor/three-engine-hbm-benchmark`; base is `develop`. Do not modify `develop`. Inspect the live repositories before changing code:
- https://github.com/struggling-student/benchmark
- https://github.com/LucianCrainic/llama3.x.c

**Central research question:** How does the evolving custom `llama3.x.c` C engine compare with current CPU vLLM and llama.cpp on the same Llama 3.1 8B model, particularly in *measured HBM bandwidth usage and sustained decode efficiency* on dual-socket Intel Xeon CPU Max nodes?

Keep the project small, legible, reproducible, and useful for repeated experiments as the C kernels evolve. Refactor aggressively where warranted, but reuse tested infrastructure rather than rewriting it merely for style.

## Repository-specific baseline to audit
The benchmark already has `src/llm_bench/{backends,runner,api_client,hardware,providers,telemetry,results}.py`, a pinned-model/artifact preparation path, YAML profiles, Slurm integration, deterministic workload manifests, result schemas and tests. CPU flat/cache detection and symbolic `hbm`/`ddr` NUMA binding are present. Existing `telemetry.py` advertises `memory_bandwidth_collection: False`; *actual bandwidth measurement is missing*. Current offline native vLLM and llama-bench metrics have different boundaries and cannot legitimately be divided to claim a speedup.

The C engine currently exposes `build/release/run` and `build/release/runq`, `--prompt-file`, `--benchmark`, `--generation-length`, `--json` (structured prefill/decode/TTFT/throughput), `LLAMA_PROFILE=1` (kernel-phase timings), `LLAMA_PLACEMENT` and page-residency checks, and `LLAMA_SOCKETS` for socket-aware runs. Inspect its *current code and supported checkpoint formats*; these interfaces can change during development. The C engine's `tools/compare_engines.py` compares logits between its own configurations; it is not an end-to-end three-engine benchmark.

## Scope and comparison matrix
Use exactly **one primary model**: `meta-llama/Llama-3.1-8B-Instruct`, with pinned source revision and tokenizer. Generate native-C, GGUF, and Hugging Face artifacts from the same source, recording conversions, tensor/quantization transforms, hashes, and effective storage/compute/activation precision.

Minimal experiment suite (warmups plus >=3 measured repetitions, configurable):
1. **Decode / HBM streaming:** 128 input / 256 generated tokens, concurrency 1; primary benchmark, report steady-state decode rather than blending prefill.
2. **Prefill / compute:** 2048 input / 32 output, concurrency 1.
3. **Long-context KV sensitivity:** 8192 input / 128 output, concurrency 1, only when the engine/configuration supports it.
Optional **concurrency 4** throughput treatment only when every participating backend supports genuinely equivalent multi-request execution; label partial results separately. No uncontrolled sweep of ten or more workloads.

Prioritize a genuinely comparable BF16 treatment **only after checking what BF16 means in each engine** (weight storage, compute, intermediate/activation and KV formats). Then add INT8/Q8 and FP32 where supported. Do not label Q8_0 weight quantization and W8A8 activation quantization as equivalent. Unsupported or materially different formats must be shown as distinct treatments, not silently cast, approximated or omitted. Avoid claiming BF16 C execution has BF16 stored weights without evidence.

The main hardware plan is flat-mode, **one-socket local HBM** versus **two-socket local HBM / socket-aware topology**. Include same-engine DDR placement as a control and cache-mode nodes as a separate comparison regime. The often-quoted ~1 TB/s is a *dual-socket aggregate achievable bandwidth* (not the expected single-socket denominator), and the effective measured STREAM ceiling should be supplied per node/topology rather than hard-coded. Keep 1-socket, 2-socket TP, and two independent socket-local instances distinct; do not conflate TP, thread-count, NUMA placement, precision, or batching with backend identity.

## Required architecture and measurement contracts
Implement a small backend-adapter interface for `llama3xc`, `llamacpp`, `vllm`; explicit executable/build/version configuration; shared model/workload/placement specification; preflight; experiment runner; normalized results; and concise comparison report. Preserve stable raw evidence, CLI commands, exit codes, stderr, code commit SHAs, model artifact hashes, NUMA topology, thread affinity, build flags and environment settings. Do not require modifications to the C engine except a minimal, separately documented interface fix if unavoidable.

**Fairness is mandatory.** Use the same exact prompt/token budget, tokenizer policy, sampling mode (prefer greedy), EOS/stop semantics, warmup policy, number of processes/sockets and measured boundaries. Validate input token IDs/counts and actual produced tokens. Never compare a C engine-internal TTFT directly with vLLM/llama.cpp streaming-server TTFT, nor `llama-bench` forward-only with `vllm bench throughput`, as a controlled ratio. Design either a genuinely common measurement path or explicitly separate (A) comparable request-level and (B) engine-native/kernel-level tracks with boundary labels and descriptive-only comparisons. A new persistent C driver is optional if essential and justified; do not create a large C HTTP-server project by default.

Record **per phase** where defensible: TTFT with its exact boundary, prefill tokens/s, decode tokens/s, inter-token time or TPOT, output tokens/s and aggregate throughput where applicable, p50/p95 (across real observations), cold model load time separately, failure/count warnings, and per-engine kernel profiling. Do not present profiler phase categories from different engines as identical if their scopes differ. Support `perf`/native phase profiling as optional diagnostics, never as mandatory dependencies.

**HBM telemetry is a primary deliverable, not a TODO.** Implement a pluggable, permission-aware collector for validated Xeon Max HBM and DDR memory-controller counters (e.g. supported PCM/LIKWID/perf uncore methods after confirming their event definitions and access). Measure actual HBM read/write bytes and GB/s **per socket and aggregate**, distinguish DDR, and align counters with prefill vs steady-state decode measurement windows. Capture a bandwidth timeline (sampling cadence documented), sustained average and variability, and percent of a topology-matched measured STREAM ceiling. Compare achieved bandwidth utilization and optionally time above a stated threshold; do not equate one peak sample with sustained busy memory. Hardware uncore counters may be node/socket-wide rather than process-specific: explicitly flag their scope, require isolated allocations for attribution, account for background traffic, and never infer measured GB/s as `model_size × tokens/s`. An analytical traffic estimate is a separate labeled metric. If instrumentation, calibration, or isolation cannot be validated, emit `null` and a clear warning rather than synthetic HBM numbers.

Flat mode: verify actual NUMA/HBM/DDR identities on the execution node, effective CPU affinity, page residency of model weights/KV/workspace where possible, and any page migration/spill. Existing llama.cpp and vLLM may be directed using `numactl` and runtime settings, but *requested membind does not prove actual HBM residency*, especially across mmap/first-touch, subprocesses, and TP workers. Test binding methods and report observed placement rather than assuming they work. Cache mode: label hardware-managed HBM cache; never report it as explicit all-HBM placement. Do not assume the flat-mode node is Slurm-schedulable; support both direct isolated flat-node execution and scheduler-managed cache jobs using site configuration.
